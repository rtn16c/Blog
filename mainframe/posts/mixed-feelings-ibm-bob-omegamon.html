Mixed Feelings: Using IBM Bob to Install OMEGAMON for Db2

4 November 2026
omegamon parmgen ibm-bob ai

As the title says, I have mixed feelings about AI.

It's an excellent tool for busy work, particularly for repetitive tasks you know how to do well like writing documentation or generating JCL skeletons. I even used it to redo the HTML and CSS for this blog site, plus generate some fun little web-based mainframe tools to play with.

But in the context of learning and doing new things, I'm still a little sceptical. Nothing can beat the learning experience of getting into software yourself and pressing buttons just to see what happens (and preferably breaking something so you have to learn how to fix it).

Recently, I've acquired an IBM Bob subscription, so I decided to put it to the test.

We will be using Bob to help install an OMEGAMON upgrade — as someone who has never touched OMEGAMON or PARMGEN before.

About IBM Bob

IBM Bob is IBM's AI-powered development assistant. It runs in a fork of VS Code, so you can create and give it access to projects.

I'm on the IBM Bob Pro Plan — the cost is $20 USD (rounds up to about $30 AUD) a month for 50 'Bobcoins'.

To put this into perspective, a small query usually uses about 0.2 of a Bobcoin. As the requests grow larger and more programmatically complex, they can take 1 or 2 entire Bobcoins.

One important distinction to note is that there is IBM Bob (for desktop) and then there is IBM Bob Premium Package for Z (for mainframes). So IBM Bob may not necessarily be as helpful when it comes to mainframe-specific questions without the Premium Package for Z. This is evident in my experiences with Bob so far.

IBM Bob functions similarly to LLMs and code assistants that most people will be familiar with having on their desktop, like Claude or ChatGPT.

Starting the OMEGAMON Installation

Prerequisites

  • One of our other systems programmers has already installed OMEGAMON Base and OMEGAMON for CICS — I just need to slap OMEGAMON for Db2 on top of it.
  • I will need to rerun PARMGEN and set up the Db2 component.
  • I got OMEGAMON for Db2 as a CBPDO package from IBM and uploaded it to a ZFS in USS prior to starting.

The Installation

Installation was done with SMP/E. My first mainframe internship was two years of SMP/E so that is muscle memory by now, and I got the FMID installed without much trouble.

  • Receive FMID
  • Allocate some datasets and add them to the target zone DDDEFs so we can apply the FMID. Note: the exact specifications for what datasets to add and their allocations are always found in a product's Program Directory, along with a load of other useful install information.
  • Apply the FMID
  • Accept the FMID

And that's pretty much it.

The Deployment

This is where I had no idea what was going on.

As mentioned briefly in the introduction, I've never used OMEGAMON or PARMGEN before. I did launch the PARMGEN menu initially, saw a bunch of acronyms and options I didn't understand, and then decided I needed some assistance.

PARMGEN is a set of panels used to customise OMEGAMON RTEs (Runtime Environments). It generates JCL based on parameters you enter and runs you through the basic submission flow of all of them.

Since this is all happening on a test system, I decided to feed Bob the relevant documentation pages from IBM's site, get it to shorten and summarise the information for me, and wing it.

This is the initial prompt I used — keep in mind I'm not an expert prompt engineer or anything, I just typed what I wanted:

I'm installing OMEGAMON for Db2. I have completed the SMP/E installation and now I need to use PARMGEN to customise it. I have never used PARMGEN. I am happy to accept default or recommended values for most of the parameters. So far I have opened PARMGEN and looked at the options available on the main panel. Can you read through these pages and summarise the key steps I need to perform with simple explanations: [Plus a whole list of document links, most of which can be found on the OMEGAMON shared documentation pages]

The reply is a little long-winded to put the full thing in a blog post. Basically, the response was a quick rundown of what PARMGEN actually is, and then a nice step-by-step list of everything I needed to do. This was by far my favourite part of the response, as often when we are learning something new the biggest obstacle is not even knowing where to start.

Summary — Your Checklist [ ] 1. Decide: Full RTE (recommended for you) [ ] 2. Gather: HLQ, SMFID, TEMS node name, Db2 SSIDs, SDSNLOAD path, STC userids, port [ ] 3. Allocate PARMGEN work datasets [ ] 4. Edit WCONFIG (use guided panels first time) [ ] 5. Validate (KCIJPVAL) — fix any errors [ ] 6. Generate (KCIJPGEN) [ ] 7. Allocate RTE datasets (KCIJPALO) [ ] 8. Copy members (KCIJPCPY) [ ] 9. Submit RACF/security job [ ] 10. Copy STCs to PROCLIB [ ] 11. Submit Db2 BIND jobs for each SSID [ ] 12. APF-authorise the runtime load library [ ] 13. Start Hub TEMS STC, then Db2 agent STC

I was also able to ask Bob clarifying questions, like 'What is in RTE?' and 'Where do I find [this] sample job?'. Most of the time it was correct — occasionally it did send me on a wild goose chase for a dataset member that did not exist or was in a different location to where it said it was.

The downside of relying on Bob's assistance for this task is I didn't actually know what I was doing or why I was doing it, and I don't think I was learning or retaining all that much information. I was just relying on Bob to direct me.

This is fine for learning on a test system. It is less fine for working on things in production.

Encountering Runtime Errors and Setting Up a Skill

After the PARMGEN process was completed, I needed to run the product. Unfortunately the first time I tried to run the started tasks, they were spitting out error messages that I had no idea what to do with.

Usually, investigating error messages involves hours of trawling through hundred-page documents.

This seemed like a good opportunity to get Bob to do that for me and experiment with the 'Skills' feature.

Basically, a skill is a reusable set of instructions Bob can call on when you ask it to do tasks that call for certain 'skills'. Depending on what you make a skill for, it can also reduce token consumption when compared to having the AI perform tasks from first principles.

Since this version of Bob isn't as knowledgeable about mainframe tasks as the Bob Premium Package for Z, I decided to make it a skill called 'Look up OMEGAMON docs'. So any time I ask an OMEGAMON-related question, Bob should use this skill to consult the IBM documents rather than relying on what it's been trained on or what it can find on the web.

That was the idea, anyway.

But I ran into some more issues setting this up — I had to troubleshoot the troubleshooting!

Issue One

Unfortunately IBM blocks scraping of their documentation website. I sent Bob a collection of links to download and save, and it returned to inform me of this:

"The PDF is reachable. The IBM Docs HTML pages are blocked (403) when accessed programmatically from this machine — they require a browser session. That means a fetch-and-cache script can only reliably download the PDF automatically; the HTML pages need to be saved manually by the user (browser → Save As)."

I ended up having to save a good portion of the document web pages myself, which was a bit of a pain!

Nevertheless, we persist.

Issue Two

Bob was able to fetch the PDF downloads, and once I had manually saved the HTML pages it started to create a look-up skill. The PDFs themselves were my second issue — Bob ended up eating more of my tokens trying to read them after I asked a question and it invoked the new skill.

"The PDF text isn't grep-searchable — I need to read content pages directly…" and "The kdpuge5.pdf is a binary PDF and isn't readable as text through this tool."

Perhaps in hindsight it would have been better to have Bob read the PDFs once and write a summary of important points in a text file — it kept re-searching the entire 4,000-page PDF each time I asked a question.

At one point it even told me a variable I was looking for did not exist, only for me to Google it and find the document page pertaining to it in about 30 seconds.

So while the skills function was fun to play with, I'm not entirely sure it saved me much time or tokens — at least, not in the way I ended up using it. Perhaps I need to take a prompt engineering course.

A Useful Find: Adding a New Db2 Subsystem Without Re-Running PARMGEN

Bob did help me identify two jobs to run outside of PARMGEN to update an already-deployed RTE without having to go back through the entire PARMGEN process.

If you want to add a Db2 subsystem to your OMEGAMON for Db2 monitoring after it's already deployed:

  1. Add the Db2 subsystem details to your RTE Config member in the *.**.WCONFIG dataset.
  2. Run $PARSE from the same dataset and make sure there are no errors in $VALRPT.
  3. In the *.**.WKANSAMU dataset, run KCIJPW2R to rebuild the runtime datasets with the parameters parsed from $PARSE.
  4. Bounce the OMEGAMON STCs.

The new Db2 subsystem will now be accessible for monitoring.

What I Got Out of It

AI is here to enhance our skills and make our jobs easier — but using it to replace a knowledgeable professional is irresponsible.

Likewise, you should be careful when using it for learning, as it can easily hallucinate answers or put you on the wrong path.

What it's good for What it's not good for
Asking 'Where do I begin?' In-depth technical questions — especially if you're asking without the knowledge to back it up. AI can often hallucinate answers that sound correct but are not.
Finding sample job locations. Searching thousands of pages of documentation (both in PDF form and from IBM) — this is what ended up using a lot of the coins.
Well-documented tasks with loads of training data available (for example, Bob helped revamp my blog with simple HTML, CSS, and JavaScript). Mainframe-specific tasks.*
Small tasks. Complex tasks with large context windows, like reading a 4,000-page PDF (these will eat up a lot of your coins).

*But I will give Bob the benefit of the doubt, as I was on a desktop plan and not a premium package (for mainframe).

Transparency

I also have one final gripe with the ability (or lack of ability) to see what Bob is actually doing behind the scenes.

In previous versions of Bob, users were able to see which models Bob was using and even direct it to only use a certain model. This is no longer possible. It seems a lot of the back-end has been hidden from the end user, which if you're anything like me, you do not appreciate.

This becomes particularly important when you're using AI in a work context and you need to know what model generated things — for intellectual property reasons, security and data handling, and auditability.

Intellectual property: different models have different training data, licensing terms, and stances on code generation and copyright. If you're generating code or documentation at work and can't identify the underlying model, you can't meaningfully assess whether the output carries any IP risk.

Security and data handling: in a work environment, prompts frequently contain sensitive context — internal system names, dataset naming conventions, security product setups. Depending on the model behind the scenes, that information may or may not be used for training, retained on external servers, or subject to different data residency requirements. Without visibility into what model is active, you can't make an informed decision about what you should and shouldn't be putting into a prompt.

Auditability: some organisations require that AI-generated content — particularly anything that touches production configuration, security definitions, or compliance documentation — be traceable back to the tool and model that produced it. "IBM Bob generated it" is not specific enough if Bob could be routing your request through any number of different underlying models depending on the task.

None of this means Bob is doing anything wrong or unsafe — but transparency is a prerequisite for responsible enterprise use, and hiding that information makes it harder to trust the tool in the environments where the stakes are highest. I hope it's something IBM revisits as enterprise adoption grows.

The Final Verdict

I came into this journey sceptical and I'm leaving… still a little sceptical, but with a bit more nuance to my position than 'Ew, AI is stealing our jobs'. The bottom line is yes, I will continue to use AI — but selectively, and with my own knowledge to back me up rather than as a crutch.
